# Lab 7：Network Driver 实验与答辩记录

## 1. 实验目标

本实验为 xv6 的 E1000 千兆以太网控制器补全设备驱动，理解操作系统如何通过内存映射寄存器、DMA 描述符环和中断与网卡交换数据，并验证以太网、ARP、IPv4、UDP 和 DNS 数据路径。

本实验对应 `net` 分支，核心任务为：

- 实现 `e1000_transmit()`，把协议栈生成的以太网帧交给网卡发送。
- 实现 `e1000_recv()`，回收网卡收到的数据包并交给 `net_rx()`。
- 正确管理描述符和 `mbuf` 的所有权，处理环满、并发和异常数据包。
- 通过 ping、单进程 UDP、多进程 UDP 和 DNS 官方测试。

## 3. E1000 与描述符环

驱动和网卡共享发送、接收两个环形描述符数组。每个描述符保存数据缓冲区地址、长度、控制位和状态位。网卡通过 DMA 直接读写内存中的数据，不需要 CPU 逐字节搬运。

描述符的所有权通过寄存器和状态位转换：

```text
发送：驱动填写 TX 描述符 -> 推进 TDT -> 网卡 DMA 读取 -> 网卡置 DD
接收：网卡 DMA 写入 RX 缓冲区 -> 网卡置 DD -> 驱动取包 -> 推进 RDT
```

`TDT` 指向驱动下一次准备提交的发送槽。`RDT` 表示驱动最后归还给网卡的接收槽，因此驱动下一次检查 `(RDT + 1) % RX_RING_SIZE`。

## 4. 发送路径实现

发送函数的主要流程：

1. 获取 `e1000_lock`，串行化多个进程的并发发送。
2. 读取 `TDT` 并定位发送描述符。
3. 检查 `DD`。若未置位，说明网卡仍拥有该槽，发送环已满，返回 `-1`。
4. 若该槽保存了旧 `mbuf`，此时网卡已经完成 DMA，可以安全释放。
5. 填写数据地址、长度及 `EOP | RS` 命令，清除 `DD`。
6. 执行内存屏障，再推进 `TDT` 通知网卡。

`EOP` 表示该描述符是一个完整包的结尾；`RS` 要求网卡完成后回写状态，使驱动之后能通过 `DD` 判断该槽是否可复用。

发送缓冲区不能在提交后立刻释放。DMA 是异步的，网卡此时可能仍在读这块内存；只有同一槽再次被使用且 `DD` 已置位时，旧缓冲区才归还驱动。

## 5. 接收路径实现

E1000 产生接收中断后，`e1000_intr()` 确认中断并调用接收函数。接收函数循环处理所有已经置位 `DD` 的描述符：

1. 根据 `RDT` 找到下一个待处理槽。
2. 检查 `DD`；未置位说明当前没有更多数据包。
3. 为该槽预先分配新的 `mbuf`。
4. 用描述符中的长度更新旧 `mbuf`，并把新缓冲区地址挂回描述符。
5. 清除状态位，执行内存屏障并推进 `RDT`，把槽归还网卡。
6. 释放网卡锁；若包以 `EOP` 结束且无错误，调用 `net_rx()`，否则释放坏包。

若新缓冲区分配失败，驱动丢弃当前包、清除描述符并继续复用原缓冲区，避免将空地址交给 DMA。

## 6. 并发、锁与内存顺序

发送路径可能由多个 CPU 上的进程同时进入，接收路径由设备中断触发，因此对描述符环、缓冲区指针和尾寄存器的修改均由 `e1000_lock` 保护。

驱动在调用 `net_rx()` 前释放锁。协议栈收到 ARP 请求后可能立即生成 ARP 应答并重新调用 `e1000_transmit()`；若仍持有同一把锁，会发生自死锁。

推进 `TDT` 或 `RDT` 前执行 `__sync_synchronize()`，保证描述符字段和缓冲区地址先对设备可见，再转移所有权。否则 CPU 或编译器重排可能让网卡观察到更新后的尾指针却读到尚未完整填写的描述符。

## 7. 调试与问题记录

首次构建出现 `can't link soft-float modules with double-float modules`。原因是 Ubuntu 26.04 的新 RISC-V 工具链对 C 文件采用了指定 ISA/ABI，而 `.S` 文件仍使用隐式规则的默认 ABI。为 CFLAGS 和 ASFLAGS 统一设置 `-march=rv64gc -mabi=lp64` 后解决。链接阶段的 RWX segment 提示来自 xv6 教学链接脚本，不影响实验。

功能验证使用官方 `grade-lab-net`。测试会在宿主机启动 UDP 服务，并通过 QEMU 用户网络连接 xv6，因此还同时覆盖中断、ARP、IP、UDP、套接字唤醒和 DNS 解析路径。

## 9. 答辩高频问题与参考回答

### Q1：什么是 DMA？为什么网卡使用 DMA？

DMA 允许设备直接访问主存。CPU 只需准备描述符和缓冲区，再通知设备；网卡自行读写数据并在完成后中断 CPU，减少逐字节拷贝和轮询开销。

### Q2：描述符环为什么设计成环形？

固定大小的环可以重复利用内存，用头尾位置区分生产者与消费者，避免每个数据包动态创建硬件队列结构，并适合驱动和设备异步流水工作。

### Q3：发送时为什么先检查 DD？

`DD` 表示网卡已完成该描述符。若它未置位就覆盖描述符或释放旧缓冲区，网卡可能发送被篡改的数据或访问已释放内存。

### Q4：为什么发送环满时返回 -1，而不是覆盖最旧的数据包？

未完成的描述符仍由设备拥有，不能覆盖。返回失败让上层释放本次 `mbuf`，保证内存和数据的一致性；更复杂的驱动也可以选择阻塞或排队。

### Q5：EOP 和 RS 分别有什么作用？

`EOP` 标记一个数据包的最后一个描述符，本实验每包只使用一个描述符；`RS` 要求网卡在发送完成后报告状态，随后驱动才能观察到 `DD`。

### Q6：接收时为什么必须先准备替换缓冲区？

旧缓冲区要交给协议栈，原描述符仍需一个有效地址供网卡接收下一包。先替换再归还描述符，可以清楚地完成缓冲区所有权转换。

### Q7：为什么不能持有 e1000_lock 调用 net_rx？

`net_rx()` 可能处理 ARP 请求并同步调用发送函数。发送函数也要获取 `e1000_lock`，而 xv6 自旋锁不可重入，因此持锁调用会自死锁。

### Q8：内存屏障解决什么问题？

它保证 CPU 对描述符内容的写入先于尾寄存器更新对外可见。尾寄存器是所有权交接点；若写入顺序被重排，设备可能读取半初始化描述符。

### Q9：网卡如何通知 CPU 收到了包？

初始化时驱动在 `IMS` 打开 RXDW 接收完成中断。网卡写回描述符后经 PCI/PLIC 触发外部中断，内核在中断处理中读取并确认 `ICR`，随后扫描接收环。

### Q10：ping 和本实验中的 UDP/DNS 各验证了什么？

ping 测试基本双向网络通信；单进程 UDP 验证发送、接收和协议栈；多进程 UDP 验证并发和唤醒；DNS 还验证域名报文编码、外部网络转发和响应解析。

### Q11：如果接收包有错误或不是完整包，如何处理？

驱动检查 `errors` 和 `EOP`。只有无错误的完整包进入协议栈，其余包释放；无论是否丢弃，都要为描述符补充缓冲区并推进 `RDT`，避免接收环停住。

### Q12：轮询和中断驱动各有什么优缺点？

轮询简单且高负载下能减少频繁中断，但空闲时浪费 CPU；中断在低负载下高效，但高速收包时可能产生中断风暴。真实网卡常采用中断合并或 NAPI 式混合方案。
