# Lab 8：Locks 实验与答辩记录

## 1. 实验目标

本实验在保持 xv6 并发正确性的前提下，降低两个高频内核锁的竞争：物理页分配器原有的全局 `kmem` 锁，以及块缓存原有的全局 `bcache` 锁。实验不仅检查功能，还统计每把自旋锁执行 test-and-set 失败的次数，因此需要根据数据访问方式重新划分共享状态。

本实验对应 `lock` 分支，包含：

- 为每个 CPU 建立独立物理页空闲链表，并支持批量窃取。
- 把块缓存组织为哈希桶，每个桶使用独立自旋锁。
- 处理缓存未命中、跨桶迁移和同一磁盘块唯一副本问题。
- 通过锁争用专项测试和完整 `usertests`。

## 3. 每 CPU 物理页分配器

### 3.1 原实现的瓶颈

原来的所有空闲页都在 `kmem.freelist` 中。任意 CPU 调用 `kalloc()` 或 `kfree()` 都必须获取同一把自旋锁。在两个进程反复扩张和缩小地址空间时，两个 CPU 会对同一缓存行执行原子交换，造成大量自旋和缓存一致性通信。

### 3.2 数据结构与本地快路径

新的 `kmem[NCPU]` 为每个 CPU 保存一把锁和一个空闲链表。释放页时先关闭中断、读取 `cpuid()`，再把页插入当前 CPU 的链表；分配页优先从当前 CPU 链表弹出。不同 CPU 的正常分配与释放不再接触同一把锁。

读取 `cpuid()` 时必须禁止中断，因为进程若在读取 CPU 编号后被抢占并迁移，就可能操作错误的本地结构。本实现从读取编号到完成链表操作都由 `push_off()/pop_off()` 包围；内部 `acquire()` 的关中断操作可以安全嵌套。

### 3.3 批量窃取

系统初始化由 CPU 0 执行，因此所有物理页最初位于 CPU 0 的链表。其他 CPU 本地链表为空时，依次检查其他链表，并一次最多取走 64 页：当前请求直接返回一页，其余页放进本地链表。

若每次只偷一页，启动后的远程分配仍会频繁竞争 CPU 0 的锁。批量窃取把一次跨 CPU 同步的成本分摊到后续最多 64 次本地分配，同时避免长时间遍历整条空闲链表。

## 4. 哈希化块缓存

### 4.1 原实现的瓶颈

原 `bcache` 使用一把全局锁保护全部缓冲区、引用计数和 LRU 链表。即使两个进程读取完全不同的文件块，每次 `bread()`/`brelse()` 仍会竞争同一把锁，且移动 LRU 链表增加了临界区长度。

### 4.2 哈希桶与命中路径

本实现使用 31 个桶：

```text
bucket = (dev XOR blockno) % 31
```

每个桶拥有独立双向链表和自旋锁。查找、增加/减少 `refcnt` 只需锁定目标块所在的一个桶。磁盘 I/O 仍由每个 `buf` 的睡眠锁保护，绝不在桶自旋锁内执行。

31 大于缓存缓冲区数 `NBUF=30`，能够把并发测试中的连续热点块充分分散，又不会建立过多无意义的锁。

### 4.3 未命中与唯一副本

同一 `(dev, blockno)` 在缓存中必须最多出现一次。两个 CPU 同时未命中时，如果各自直接选择空闲缓冲区，就可能创建两个副本，导致写入一致性错误。

本实现仅在缓存未命中路径获取短临界区 `bcache.evict` 锁，并在获得它后重新检查目标桶：

1. 若另一 CPU 已经插入该块，直接增加引用计数并返回。
2. 优先复用目标桶内 `refcnt == 0` 的缓冲区。
3. 若目标桶没有空闲项，逐桶查找一个未使用缓冲区。
4. 在原桶锁内把它的 `refcnt` 设为 1 并摘链，随后插入目标桶。

淘汰协调锁只覆盖元数据操作，不覆盖睡眠锁等待或磁盘读写，因此不会把正常缓存命中串行化。整个迁移过程一次只持有一把桶锁，避免桶锁顺序造成死锁。

## 5. 自旋锁与睡眠锁的分工

- 自旋锁用于极短的链表、引用计数和所有权更新；持有时 CPU 不睡眠。
- 每个 `buf` 的睡眠锁用于保护磁盘块内容，磁盘 I/O 可能等待中断，因此必须允许进程睡眠。
- `refcnt` 防止仍在使用或已被日志系统 pin 的缓冲区被淘汰。
- `bget()` 在获取睡眠锁之前释放桶锁，避免磁盘或其他使用者导致长时间自旋。

## 6. 调试与性能优化记录

第一版使用 13 个哈希桶，块缓存功能和完整 `usertests` 均正确，但官方 `bcachetest` 报告：

```text
tot= 20714
test0: FAIL
```

读取每把锁的统计后发现，`bcache.evict` 为 0 次自旋，争用全部来自多个桶锁。三个测试文件各有 10 个连续数据块，13 桶取模使它们的热点块周期性碰撞。将桶数调整为 31 后再次测试：

```text
lock: bcache.evict: #test-and-set 0
lock: bcache.bucket: #test-and-set 0
...
tot= 0
test0: OK
```

这说明锁优化不能只看“锁的数量”，还要根据工作集和哈希分布判断共享热点。另一个构建问题是新工具链的 C/汇编 ABI 不一致，通过统一 `-march=rv64gc -mabi=lp64` 解决。

## 8. 答辩高频问题与参考回答

### Q1：自旋锁适用于什么场景？

适合临界区很短、不能睡眠的内核路径。等待者占用 CPU 自旋，所以若临界区包含磁盘 I/O 或长时间阻塞，代价很高，应改用睡眠锁。

### Q2：为什么全局 kmem 锁会产生严重争用？

所有 CPU 的分配和释放都修改同一链表头和同一锁缓存行。即使物理页彼此独立，操作也被不必要地串行化，并引发原子操作和缓存行来回迁移。

### Q3：为什么读取 cpuid 必须关中断？

进程可能在中断后被调度到另一 CPU。若 CPU 编号和后续链表操作不在稳定区间内，就会把本应本地的页操作施加到另一 CPU 的链表上，破坏设计假设。

### Q4：为什么一次偷 64 页而不是一页？

批量窃取减少远程锁获取次数，把昂贵的跨 CPU 同步分摊给多次本地分配；固定上限又避免持有受害者锁遍历过久，并给其他 CPU 保留内存。

### Q5：每 CPU 链表会不会导致有空闲内存却分配失败？

不会只检查本地链表。本地为空后会遍历其他 CPU 的链表并窃取；只有所有链表都为空才返回 0。

### Q6：为什么块缓存不能简单地做到每个 buf 一把锁？

查找某个磁盘块时还不知道对应哪个 `buf`，仍需保护“块号到 buf”的全局映射和唯一性。哈希桶锁以块号定位共享范围，在可查找性与并行度之间取得平衡。

### Q7：为什么同一磁盘块只能有一个缓存副本？

若存在两个副本，两个进程可能分别修改不同副本，写回顺序决定最终磁盘内容，读者也可能看见不一致数据。唯一副本同时是该块的同步汇合点。

### Q8：未命中后为什么要二次检查？

第一次释放桶锁到获得淘汰锁之间，另一 CPU 可能已经缓存目标块。二次检查避免再分配一个副本，是典型的检查—加锁—再检查模式。

### Q9：跨桶移动为何不同时持有两把桶锁？

若不同线程以相反顺序获取两个桶锁，会形成循环等待。本实现先在原桶内保留并摘下空闲项，释放原桶锁后再插入目标桶；淘汰锁保证此过程不会与另一未命中迁移冲突。

### Q10：refcnt 和 buf 的睡眠锁有什么区别？

`refcnt` 表示有多少调用者或日志系统声明该缓存项不可淘汰；睡眠锁保证某一时刻只有一个执行流访问或修改块内容。前者管理生命周期，后者保护内容。

### Q11：为什么不用原来的全局 LRU 链表？

维护精确全局 LRU 会让每次释放缓冲区都修改同一链表，重新引入全局热点。该实验允许淘汰任意未使用项；牺牲精确 LRU 能显著降低争用且不影响正确性。

### Q12：如何证明优化有效而不仅是“感觉更快”？

`spinlock.c` 记录每把锁获取次数和 test-and-set 失败次数。官方测试直接比较 `kmem`/`bcache` 的失败总数；本实现的块缓存专项测试最终显示 `tot=0`，并同时通过功能回归。
