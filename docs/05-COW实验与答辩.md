# Lab 5：Copy-on-Write Fork 实验与答辩记录

## 1. 实验目标

把 xv6 原来在 `fork()` 时立即复制全部用户物理页的实现改为写时复制（Copy-on-Write，COW）。父子进程先共享物理页，只有某一方第一次写入时才分配私有副本，从而降低 `fork` 的时间与内存开销。

本实验对应 `cow` 分支，包含：

- 修改 `uvmcopy()`，让父子页表共享物理页。
- 使用 RISC-V 软件保留位标记 COW 页。
- 为物理页建立线程安全的引用计数。
- 在用户写页故障时复制或恢复可写权限。
- 让内核 `copyout()` 同样正确处理 COW 页。

## 2. 修改文件

| 文件 | 作用 |
| --- | --- |
| `kernel/riscv.h` | 定义软件管理的 `PTE_COW` 位。 |
| `kernel/kalloc.c` | 实现物理页引用计数、增加引用和延迟释放。 |
| `kernel/defs.h` | 声明引用计数及 `cowalloc()` 接口。 |

| `time.txt` | 记录实验投入时间。 |

## 3. 原始 fork 的问题

原版 `uvmcopy()` 对父进程的每个用户页执行：分配新页、复制 4096 字节、映射到子页表。若子进程随后立刻 `exec()`，这些复制全部浪费；当父进程占用超过一半物理内存时，即使父子从不修改共享内容，`fork()` 也会因无法分配同等数量的新页而失败。

COW 将复制推迟到真正发生写入时。只读访问可一直共享，`fork + exec` 通常几乎不需要复制数据页。

## 4. 关键设计

### 4.1 COW 页表标记

`PTE_COW` 使用 RISC-V PTE 的软件保留位第 8 位。`uvmcopy()` 对原来同时具有 `PTE_W` 和 `PTE_U` 的页：

1. 清除父 PTE 的 `PTE_W`。
2. 设置父 PTE 的 `PTE_COW`。
3. 用相同物理地址和权限建立子映射。
4. 增加物理页引用计数。

只给“原本可写的用户页”设置 COW。代码等原本只读页直接共享且保持只读；否则若误打 COW 标记，程序可能通过写页故障把真正的只读代码页变成可写页，破坏权限语义。

### 4.2 引用计数

每个可分配物理页有一个整数引用数，索引为：

```c
(pa - KERNBASE) / PGSIZE
```

计数数组由独立自旋锁保护：

- `kalloc()` 从空闲链表取页后把引用数设为 1。
- `uvmcopy()` 新增共享映射后调用 `krefinc()`。
- `kfree()` 先递减引用数；只有变为 0 才填充垃圾数据并放回空闲链表。
- 引用数小于 1 时再次释放属于双重释放，内核主动 `panic`。

系统启动时 `freerange()` 先给每个页设置一个初始引用，再调用 `kfree()` 递减为 0并加入空闲链表，从而复用统一释放逻辑。

### 4.3 写页故障

用户写只读 COW 页时，RISC-V 产生 store page fault，`scause` 为 15，`stval` 保存故障虚拟地址。`usertrap()` 调用 `cowalloc()`：

- 验证地址、PTE_V、PTE_U 和 PTE_COW。
- 若引用数为 1，说明其他共享者已经退出，无须复制，只清除 COW 并恢复 `PTE_W`。
- 若引用数大于 1，分配新页、复制旧内容、把当前 PTE 改到新页，再释放当前进程对旧页的一个引用。
- 分配失败或不是合法 COW 页时，杀死当前用户进程，而不是让内核崩溃。

### 4.4 copyout 为什么要特殊处理

`copyout()` 在内核态通过物理地址直接写用户页，不会执行用户页表下的普通 store 指令，因此不会产生 COW 页故障。如果管道 `read` 等系统调用把数据写入 COW 缓冲区而不主动拆分，父子进程会互相覆盖。

因此 `copyout()` 在每一页写入前检查 `PTE_COW`，主动调用同一个 `cowalloc()`，再通过新的物理地址复制数据。

### 4.5 非法地址边界

新增 COW 检查一度在 `copyout()` 中直接调用 `walk()`。`usertests` 传入超过 `MAXVA` 的恶意地址时，`walk()` 会 `panic`，而正确行为应是返回 `-1`。最终实现在调用 `walk()` 前检查 `va0 >= MAXVA`，恢复用户输入永远不能使内核崩溃的安全边界。

## 6. 答辩高频问题与参考回答

### Q1：COW 优化了什么？代价是什么？

它把 fork 的逐页复制变成共享页表映射，大幅减少时间和峰值内存，尤其适合随后执行 exec 的进程。代价是页表权限管理、引用计数和第一次写入页故障的额外复杂度。

### Q2：为什么父进程的 PTE 也必须清除 PTE_W？

若只让子进程只读，父进程仍能直接修改共享物理页，不触发故障，子进程会观察到父进程的修改，违反地址空间隔离。

### Q3：为什么需要独立 PTE_COW 位？

只看 `PTE_W == 0` 无法区分“原本只读”和“因 COW 暂时只读”。前者写入必须失败，后者写入应创建副本并恢复写权限。

### Q4：为什么引用数为 1 时可以不复制？

物理页只剩当前映射，没有其他进程会观察到修改。直接清除 COW 并恢复写权限即可，既正确又能在空闲内存不足时继续运行。

### Q5：为什么不能在 fork 后立刻释放父页？

父子页表仍同时指向该物理页。引用计数必须反映所有有效映射，只有最后一个映射消失时物理页才能回到空闲链表。

### Q6：页故障发生时有哪些关键寄存器？

`scause == 15` 表示 store page fault；`stval` 给出故障虚拟地址；`sepc` 指向失败的写指令。COW 修复映射后不推进 PC，返回用户态会重新执行同一条写指令并成功。

### Q7：为什么页故障处理后不把 epc 加 4？

与系统调用不同，失败的 store 尚未完成，必须重新执行。若跳到下一条指令，本次写入会被静默丢失。

### Q8：为什么 copyout 不会自动触发 COW 页故障？

它使用内核直接映射的物理地址执行 `memmove`，没有通过带 COW 权限的用户 PTE 完成写访问，所以硬件看不到对用户只读映射的违反。

### Q9：引用计数为什么需要锁？

多个 CPU 上的进程可能同时 fork、退出或处理 COW 故障。没有锁时递增和递减会发生丢失更新，可能提前释放仍在使用的页或永久泄漏页。

### Q10：修改 PTE 后为什么要考虑 TLB？

TLB 可能缓存旧的可写权限或旧物理地址。xv6 从内核返回用户页表时会执行 `sfence.vma` 刷新转换；一般系统中修改活动页表后必须显式失效对应 TLB 项。

### Q11：内存不足时如何处理 COW fault？

若该页只有一个引用，可以直接恢复写权限；若确实需要副本而 `kalloc` 失败，则返回错误并杀死触发故障的用户进程，不能让内核继续使用空指针。
